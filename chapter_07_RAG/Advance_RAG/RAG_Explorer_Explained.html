The problem

Basic RAG breaks down at scale

A single dense embedding + top-k lookup is fine for a handful of documents. On a real corpus it starts missing answers — exact IDs slip through the cracks, near-duplicates crowd out the truly relevant row, and one phrasing of a question only reaches one neighbourhood of the index.

Recall gap

Semantics miss exact terms

Ask for VWO-1357 and a purely semantic vector shrugs. Lexical signal is needed for IDs, error codes, and jargon.

Precision gap

Top-k ≠ most relevant

The vector nearest in cosine space isn't always the best answer. You need a second, sharper opinion before you trust the top rows.

Phrasing gap

One query, one blind spot

"Lockout" and "too many attempts" land in different regions. Rewriting the query widens the net before you ever search.

This explorer closes all three gaps — and shows you each fix happening.

The architecture

One model for two vectors, one DB for both

Every chunk is embedded once by bge-m3, which emits a dense semantic vector and a sparse lexical vector in a single forward pass. Both live in the same Qdrant collection.

Hybrid retrieval

Dense knows meaning. Sparse knows words.

The same chunk produces two complementary vectors. Toggle between them to see what each captures.

1,024-dimensional dense vector

A smooth point in meaning-space. "Account lockout" sits near "too many failed attempts" even with zero shared words.

cosine similarity · captures paraphrase & synonymy

Sparse lexical weights

Mostly zeros, with weight on the tokens that actually appear. This is what nails exact IDs and keywords.

Why keep both?

D

Dense wins on intent

"How does VWO handle brute-force logins?" → finds the lockout test with no keyword overlap.

S

Sparse wins on specifics

VWO-1357, bge-reranker-v2-m3, "MTU overage" → exact matches dense would blur.

Run both searches, then fuse the two ranked lists. That's the next stage. ↓

Reciprocal Rank Fusion

Merging two rankings, fairly

Dense and sparse scores aren't on the same scale, so we can't just add them. RRF ignores the raw scores and rewards rank position instead — a chunk that ranks high on either list floats up.

RRF(chunk) = Σlists  1 / (k + rank)   // k = 60 smooths out noisy tail ranks

Cross-encoder re-ranking

A sharper second opinion

Bi-encoders (bge-m3) embed the query and chunk separately — fast, but approximate. The bge-reranker-v2-m3 cross-encoder reads the query and each candidate together, so it judges true relevance far more precisely. We only run it on the ~20 fused candidates, then keep the top 4.

The vibe-coding story

From a blank folder to a live explorer

Built conversationally — describe the pipeline, generate the corpus, wire the stages, and let each screen teach what it's doing. Here's the arc.

1

Generate a realistic corpus

A seeded Python generator emits 2,000 VWO test cases across 24 modules — Jira keys, priorities, steps, expected results, tags — as a clean CSV. Deterministic, so it regenerates identically.

2

Embed once, store hybrid

Each row → one bge-m3 pass → a dense + a sparse vector → upserted into an embedded Qdrant collection with named vectors. No Docker; it's just a local file store.

3

Make every stage visible

Ingestion streams over Server-Sent Events: watch chunks form (overlap highlighted), embeddings fill a progress bar, and points land in Qdrant — live.

4

Retrieve like production

Query rewriting widens recall, dense+sparse run in parallel, RRF fuses them, the cross-encoder sharpens precision, and Groq writes a grounded answer with citations — each step rendered in the trace.

5

Degrade gracefully

No GPU or 3 GB download? A dependency-free lite backend (hashing embeddings + lexical reranker) keeps the whole UI running so the shape of every stage is identical on any laptop.
