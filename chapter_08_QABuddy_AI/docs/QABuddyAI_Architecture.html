01 — What it is

One question in, a grounded answer out

QABuddyAI is a hybrid-retrieval RAG service. When a QA engineer asks a question, it searches the team's knowledge base by meaning and by keyword at the same time, re-ranks the strongest matches with a cross-encoder, and asks a large language model to answer only from what it retrieved — tagging every claim with the source it came from. If nothing relevant is found, it says so rather than inventing an answer.

Hybrid search
Dense (BGE-M3) and sparse (BM25) vectors run together, so semantic and exact-keyword matches both surface.
RRF fusion
Qdrant merges the two result lists server-side with Reciprocal Rank Fusion — no client-side glue.
Cross-encoder rerank
bge-reranker-v2-m3 re-scores fused candidates against the question for precision at the top.
Grounded & cited
The LLM answers from retrieved context only; citations are parsed back out of the response.
Idempotent ingestion
Deterministic point IDs + a content-hash manifest mean re-runs update in place, never duplicate.
Split deployment
A Next.js UI on Vercel proxies to the model-and-data backend on a single droplet.

How a question flows

  1. The browser posts the question to the Next.js /api/ask route, which forwards it server-side to the droplet — keeping the backend URL hidden and CORS out of the picture.
  2. The backend embeds the question as both a dense and a sparse vector.
  3. Qdrant runs both vectors as prefetch legs and fuses the two ranked lists with RRF, returning up to 20 candidates.
  4. The candidate texts go to the reranker, which re-scores them against the question; the top k (default 8) survive.
  5. Those chunks become the context for Groq, which writes a grounded answer with inline [source: …] tags that are parsed back into a citation list.

05 — Getting data in

Ingestion pipeline

Ten source folders map to ten source types. run_full_ingest.py walks each folder, hands every file to the chunker for its type, then embeds and upserts the resulting chunks. It's a batch job, decoupled from the live API.

The collection is defined once

Two named vectors live side by side on every point — a dense vector and a sparse vector — and the sparse side carries Qdrant's IDF modifier so BM25 term weighting is applied at query time. Keyword payload fields get indexes so retrieval can be filtered by source_type, module, jira_id, and more.

ingest/embed_and_upsert.py

client.create_collection(
    collection_name=config.COLLECTION,
    vectors_config={
        "dense": models.VectorParams(
            size=config.DENSE_DIM, distance=models.Distance.COSINE),
    },
    sparse_vectors_config={
        # IDF pairs with the BM25 sparse embeddings (fastembed)
        "sparse": models.SparseVectorParams(modifier=models.Modifier.IDF),
    },
)

Upserts are idempotent

A point's ID is a uuid5 of source_type | source_path | chunk_index. Re-ingesting the same file writes the same IDs, so it overwrites instead of duplicating. A content-hash manifest skips unchanged files, deletes-then-re-embeds changed ones, and removes the vectors of files that disappeared.

ingest/embed_and_upsert.py

def point_id(source_type, source_path, index):
    return str(uuid.uuid5(_NAMESPACE, f"{source_type}|{source_path}|{index}"))
Note

The _NAMESPACE UUID is fixed forever. Changing it shifts every point ID, which turns the next ingest into a full duplicate set.

06 — Finding the right chunks

Retrieval pipeline

Retrieval is where hybrid search happens. The question is embedded twice — dense and sparse — and both go to Qdrant as prefetch legs of a single request. Qdrant fuses them with Reciprocal Rank Fusion and returns the merged candidate set; only then does the reranker run.

backend/retrieval.py

prefetch = [
    models.Prefetch(query=dense, using="dense",
                    limit=config.TOP_N_HYBRID, filter=qfilter),
]
if sidx:  # skip an all-stopword (empty) sparse vector
    prefetch.append(models.Prefetch(
        query=models.SparseVector(indices=sidx, values=svals),
        using="sparse", limit=config.TOP_N_HYBRID, filter=qfilter))

result = client.query_points(
    config.COLLECTION,
    prefetch=prefetch,
    query=models.FusionQuery(fusion=models.Fusion.RRF),
    limit=config.TOP_N_HYBRID, with_payload=True)

# cross-encoder rerank, then keep the top-k
ranked = rerank(question, [p.payload["text"] for p in result.points])

Filters passed from the UI — for example {"source_type": ["jira"], "module": "checkout"} — become a Qdrant Filter applied inside both prefetch legs, so the hybrid search itself is scoped, not just the final list.

07 — Writing the answer

Grounded generation

The runtime prompt is the fenced block of QABuddyAI_Generation_Prompt.md. Retrieved chunks are formatted into {context} and the user's text into {question} — using str.replace rather than str.format, because retrieved code chunks are full of curly braces that would break formatting. Groq answers at temperature 0.2, and the citations it emits are pulled back out with a small regex.

backend/generate.py

_CITATION_RE = re.compile(r"\[source:\s*([^\]]+)\]", re.I)

prompt = (load_template()
          .replace("{context}", format_context(chunks))
          .replace("{question}", question))
# ... Groq chat completion ...
citations = list(dict.fromkeys(_CITATION_RE.findall(text)))

When retrieval returns nothing, the API skips the LLM entirely and returns a fixed “not found in the knowledge base” message — the system never guesses when it has no evidence.

09 — From empty folder to running service

Build the backend

The backend is four small packages — common/ (config + embedding clients), ingest/ (chunkers + upsert), backend/ (API, retrieval, generation), and config/ — wrapped in one Docker image. Here is the order it comes together in.

  1. Scaffold the layout

    Create common/, ingest/chunkers/, backend/, config/, and eval/. Keep every service address and tuning knob in common/config.py, each overridable by an environment variable.

  2. Configure it

    Copy the template and fill in the one secret that matters plus the service URLs. In Compose these point at service names; for local dev they point at localhost.

  3. Define the Qdrant collection

    Create the collection with named dense (1024-d, cosine) and sparse (IDF modifier) vectors, then add keyword payload indexes for the fields you'll filter on. This runs once, on first ingest.

  4. Build the embedding layer

    Three thin HTTP clients in common/embedding.py: dense via TEI /embed, sparse via in-process fastembed BM25, rerank via TEI /rerank. One place to swap models later.

  5. Write per-source chunkers

    Each source type gets a chunker that turns a file into Chunk(text, metadata) objects. Metadata (source_type, module, jira_id, tc_id, …) is what makes filtered retrieval possible downstream.

  6. Ingest idempotently

    Embed each chunk (dense + sparse) and upsert with its deterministic uuid5 ID. The manifest makes the second run a fast delta, not a rebuild.

  7. Implement hybrid retrieval

    Embed the query both ways, send both as prefetch legs, let Qdrant fuse with RRF, then rerank the fused candidates and return the top-k with their payloads.

  8. Implement grounded generation

    Fill the prompt template with context and question, call Groq, and extract the [source: …] citations from the reply.

  9. Expose the API

    A FastAPI app with POST /ask (retrieve → generate → return answer + sources) and GET /health (probe Qdrant, both TEI services, and the Groq key).

  10. Containerize and run

    A python:3.11-slim image runs uvicorn; Compose brings up Qdrant, both TEI services, the backend, the UI, and nginx together. Then run the ingest once.

First run

# 1 — configure
$ cp .env.example .env        # set GROQ_API_KEY, service URLs

# 2 — bring the whole stack up
$ docker compose up -d --build

# 3 — populate Qdrant from the data folders
$ docker compose exec backend python ingest/run_full_ingest.py --source all

# 4 — confirm every service is green
$ curl -s localhost/api/health

11 — Tuning with numbers, not vibes

Evaluation

A small golden set plus a harness (eval/eval.py) turns “did that chunking change help?” into a number. Retrieval quality is measured for free; answer quality adds an LLM judge. The golden set is eval/golden_set.jsonl — one JSON object per line: a question, the expected_sources that should back it, and an optional reference_answer.

MetricWhat it measuresCost
hit-rate@kIs an expected source among the top-k retrieved chunks?retrieval only
Citation correctnessDo the answer's [source: …] citations point at chunks that actually support the cited claims?LLM judge
FaithfulnessIs every factual claim grounded in the retrieved context, with nothing invented?LLM judge

The judge is a separate Groq call at temperature 0.0 that returns strict JSON scores from 0 to 1 — so grading is deterministic and cheap to re-run.

$ python eval/eval.py            # retrieval-only — fast, no LLM cost
$ python eval/eval.py --judge    # + generation + citation & faithfulness
$ python eval/eval.py --k 8      # change the top-k cutoff
Practice

Run it after every chunking or tuning change and compare the summary line — hit-rate@k, citation correctness, faithfulness — before keeping the change.

12 — Where it runs

Deployment

The default is a single 8 GB droplet running the whole Compose stack. The public UI is split off to Vercel: the Next.js app there proxies to the droplet through its own server-side route handlers, so the browser only ever talks to Vercel and the backend URL stays private.

Vercel
Next.js UI + /api/* proxy routes. Backend address and key live in server-side env vars.
Droplet
nginx → FastAPI, plus Qdrant and the two TEI model servers. One docker compose up.
Before public

Two gates before the droplet API faces the internet: HTTPS (Caddy or nginx + Let's Encrypt) with CORS locked to the Vercel domain, and an API key on the endpoint. The UI already sends an X-QAB-Key header for the backend to check.
