QABuddyAI — Backend & Architecture

A hybrid-RAG QA knowledge assistant. It answers questions from the team's own material — code, test cases, tickets, docs, meetings, logs — and cites every source.

FastAPIQdrant BGE-M3BM25 Groq · llama-3.3-70bNext.js / Vercel Docker

§1 Overview

QABuddyAI is a Retrieval-Augmented Generation service. Two things happen: an offline ingestion pipeline turns 10 kinds of source files into searchable vectors in Qdrant, and an online query pipeline retrieves the most relevant chunks for a question and asks an LLM to answer only from them, with inline citations.

What makes it hybrid: every query runs two retrieval legs at once — a dense leg (semantic meaning, via BGE-M3 embeddings) and a sparse leg (exact keywords, via BM25) — then fuses and reranks the results. Dense catches paraphrases and synonyms; sparse catches error codes, ticket IDs, and test names. Together they beat either one alone.

10 sources→ingest →Qdrant→hybrid retrieve →rerank→Groq LLM →cited answer

§2 Architecture

The backend is a Python package split into four responsibilities, plus two frontends and a Docker service stack.

Python packages

common/ — config + embedding clients (shared)
ingest/ — chunkers, embed & upsert, batch runner
backend/ — FastAPI app, retrieval, generation
eval/ — golden-set evaluation harness

Service stack (Docker)

qdrant — vector database
tei-embed — BGE-M3 embeddings (dense)
tei-rerank — bge-reranker-v2-m3 cross-encoder
backend — FastAPI · nginx — reverse proxy
Groq (the answer LLM) is a hosted API, not a local container — only an API key is needed. TEI = HuggingFace Text Embeddings Inference, serving the embedding and reranker models.

§3 Ingestion Pipeline

Entry point: python ingest/run_full_ingest.py --source all. It walks each of the 10 data-source folders, and for every file runs its source-specific chunker, embeds the chunks, and upserts them to Qdrant. It is incremental by default.

Delta by content hash

A manifest at ingest/.state/manifest.json maps each ingested file to its SHA-256 hash:

  • Unchanged file (hash matches) → skipped.
  • Changed file → its old points are deleted, then re-chunked and re-upserted.
  • Deleted file (in manifest, gone from disk) → its vectors are removed.

Pass --full to ignore the manifest and re-ingest everything.

Per-source chunkers

Each source type has a chunker in ingest/chunkers/ that knows how to split it and what metadata to attach:

Embed & upsert

ingest/embed_and_upsert.py embeds each batch (dense via TEI, sparse via BM25) and writes points to Qdrant. Point IDs are deterministic — uuid5(source_type | source_path | chunk_index) — so re-running a file overwrites the same points instead of duplicating them.

§4 Storage & Schema

A single Qdrant collection (qabuddy) holds named dense and sparse vectors per point, created by ensure_collection():

# each point carries BOTH vectors
vectors_config       = { "dense": VectorParams(size=1024, distance=COSINE) }
sparse_vectors_config= { "sparse": SparseVectorParams(modifier=IDF) }  # BM25 + IDF

Keyword payload fields get an index so retrieval can be filtered:

source_typewhich of the 10 sources (e.g. jira, test_case) moduleproduct area (e.g. checkout) priority · statusticket / test attributes jira_id · tc_id · job_namecitation handles & filters source_paththe file a chunk came from (used for delta deletes) is_failureboolean flag on Jenkins log chunks

Each point's payload also stores the chunk text, chunk_index, content_hash, and ingested_at timestamp.

§5 Hybrid Retrieval

backend/retrieval.py · retrieve() is the heart of the system. Steps:

  1. Build filter — optional {"source_type":[...], "module":"..."} becomes a Qdrant Filter (MatchAny for lists, MatchValue for scalars).
  2. Embed query — dense (BGE-M3) + sparse (BM25). An all-stopword query yields an empty sparse vector, so the sparse leg is skipped in that case.
  3. Two prefetch legs — using="dense" and using="sparse", each returning up to TOP_N_HYBRID (20) candidates, filtered.
  4. RRF fusion — Qdrant's query_points merges the two legs server-side with Reciprocal Rank Fusion into a single ranked list.
  5. Rerank — the fused candidates go through the bge-reranker-v2-m3 cross-encoder (TEI); the top TOP_K_RERANK (8) are returned with scores + payloads.
# the two legs, fused server-side
prefetch = [
    Prefetch(query=dense,  using="dense",  limit=20, filter=qfilter),
    Prefetch(query=sparse, using="sparse", limit=20, filter=qfilter),
]
result = client.query_points("qabuddy", prefetch=prefetch,
                             query=FusionQuery(fusion=RRF), limit=20)
ranked = rerank(question, [c.text for c in result.points])[:8]
A chunk's citation handle is chosen by source_label(): JIRA key → test-case id → file path — whichever exists first.

§6 Answer Generation

backend/generate.py · answer() turns retrieved chunks into a cited answer:

  • Loads the prompt template — the fenced block of QABuddyAI_Generation_Prompt.md (cached after first read).
  • Formats the chunks into a numbered context block, each tagged with its source label and type.
  • Fills the template with .replace() (not .format() — retrieved code chunks are full of { } braces that would break formatting).
  • Calls Groq (llama-3.3-70b-versatile, temperature=0.2, max_tokens=1500).
  • Extracts the citations actually used via the [source: …] pattern, de-duplicated in order.
If retrieval returns no chunks, the API never calls the LLM — it returns a fixed "Not found in the knowledge base" message. The model is only ever asked to answer from supplied context, so it does not fabricate.

§7 API Endpoints

Defined in backend/main.py (FastAPI, CORS open — intended to sit behind nginx/VPN).

POST  /ask

Ask a question, get a grounded answer with citations and ranked sources.

REQUEST

{
  "question": "How is guest checkout tested?",
  "filters": { "source_type": ["test_case"] },
  "top_k": 8
}

question required (min 3 chars). filters & top_k (1–20) optional.

RESPONSE

{
  "answer": "Guest checkout is covered by… [source: TC-1042]",
  "citations": ["TC-1042"],
  "sources": [{
    "n": 1, "source": "TC-1042",
    "source_type": "test_case", "score": 0.91,
    "module": "checkout", "text": "…"
  }]
}

Errors: 502 if retrieval or generation fails (message says which).

GET  /health

Liveness of every dependency — Qdrant (with point count), both TEI services, and whether the Groq key is set. Returns {"healthy": bool, "services": {…}}; healthy is true only if all report ok.

§10 Deployment

  • Backend + services: docker-compose up brings up Qdrant, both TEI services, the FastAPI backend, and nginx.
  • Web frontend: web/ is a Next.js 14 app on Vercel — /api/ask and /api/health proxy to the backend; chat UI in app/page.tsx.
  • Internal frontend: frontend/app.py is a Streamlit app for quick internal use.
  • Scheduled refresh: ingest/cron_hourly.sh re-runs the delta ingest (JIRA-via-MCP sync still pending).

§11 Run Locally

# 1 · services
docker-compose up -d          # qdrant + TEI ×2
# 2 · configure
cp .env.example .env          # then set GROQ_API_KEY
pip install -r requirements.txt
# 3 · ingest the knowledge base
python ingest/run_full_ingest.py --source all
# 4 · serve the API
uvicorn backend.main:app --reload --port 8000
# 5 · ask
curl -X POST localhost:8000/ask -H "Content-Type: application/json" \
     -d '{"question":"How is guest checkout tested?"}'
